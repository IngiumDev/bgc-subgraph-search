## MongoDB cohort API extensions for regex-based FG search and domain keyword mining

To support advanced biosynthetic gene cluster (BGC) and mobile genetic element profiling, the MongoDB “single cohort” API was extended in two main directions:

1. **Regex-like FG queries over Pfam domain architectures** (FGRegex-style search at database level).
2. **Convenience mining of Pfam domains by description keywords** (e.g., mobile elements, toxins).

These additions integrate with cohort-level search (`cohort_domain_search`) via an updated `get_FG2gc_id(...)` interface that can switch between exact-FG lookup and regex-based protein retrieval.

### Updated: `get_FG2gc_id(...)` (now supports regex search)

`get_FG2gc_id(...)` previously resolved:

`FG (exact) → protein_id list → gc_id list`

It has been extended with an `is_regex_search` flag:

- `is_regex_search = False` (default): exact FG lookup via `get_FG2prot_id(...)` (collection `FG_interproscan_Pfam`).
- `is_regex_search = True`: regex-like FG query evaluation via `get_FG2prot_id_regex(...)`, which searches proteins by matching a Pfam-domain architecture regex against the compact FG string.

This makes downstream modules (e.g., `cohort_domain_search`) agnostic to whether the user provided exact FG identifiers or advanced FGRegex patterns.

## Domain keyword mining utilities

Two utility functions provide quick access to Pfam domains based on substring matches in the Pfam description field (case-insensitive), using a full collection scan:

- `get_mobile_element_domains(prj_name, client, search_patterns=["integrase","integrative","transposon"])`
- `get_bacterial_toxin_domains(prj_name, client, search_patterns=["toxin"])`

Both call the shared helper:

- `_get_domain_by_pattern(prj_name, search_patterns, client, col_name="protein_pfam_domain")`

Return type:
- `{Pfam_id: Pfam_description}` for all domains whose description contains any of the provided patterns.

These functions are primarily intended for exploratory query construction (e.g., identifying mobile element marker domains to build FGRegex patterns).

## Regex-based FG query execution (new)

### `get_FG2prot_id_regex(FG_lst, DB_name, client, ...)`

Evaluates a list of advanced FG queries and returns:

- `{queryFG: [protein_id, ...]}`

Each query is executed independently via `search_protein_by_FG(...)`, enabling batch processing of multiple domain-architecture patterns.

---

### `search_protein_by_FG(queryFG, DB_name, client, ...)`

Core implementation of regex-based functional-group search over protein Pfam architectures. The function returns a list of proteins whose compact FG string matches a compiled regex derived from `queryFG`.

Key steps:

1. **Extract mandatory Pfam domains** from `queryFG` using `get_mandatory_domains(...)`.
2. **Choose the rarest mandatory domain** (minimum number of proteins) to minimize the candidate set.
3. **Candidate retrieval**:
   - query `protein_pfam_domain` for proteins containing the rarest mandatory Pfam (`distinct("protein_id", {"Pfam_id": min_pfam})`)
4. **Validation against full architecture**:
   - fetch compact FG strings from `FG_interproscan_Pfam` in batches
   - normalize FG string (`replace(":::", "")`)
   - apply regex match via `matches_fg_query(...)`

This “rarest-domain anchoring” strategy reduces database load compared to scanning all proteins.

---

### `compile_fg_query_pattern(queryFG)`

Converts the user-facing FG query syntax into a compiled regex pattern:

- normalizes delimiters (removes commas/spaces)
- expands `" *"` into `".*"`
- handles leading `*` by prefixing a dot (`".*"`) to keep the regex syntactically valid
- raises a clear `ValueError` on invalid patterns

Output:
- `re.Pattern` usable by `matches_fg_query(...)`.

---

### `get_mandatory_domains(FG_query)`

Parses a query string and returns a **unique list** of Pfam IDs that are unambiguously mandatory, i.e., required for matching and suitable for candidate anchoring.

Rules:

- ignore wildcard-only fragments: `.`, `.*`, `*`
- ignore fragments containing `|` (OR, not strictly mandatory)
- match Pfam IDs by `PF\\d{4,6}`
- treat Pfam as optional if followed by:
  - `?`, `*`, or `{0,...}` (minimum count = 0)
- otherwise treat as mandatory

If no mandatory domains are found, a warning is emitted and `search_protein_by_FG(...)` raises an error (cannot anchor candidates).

---

### `count_prots_per_pfam(pfam_domains, client)`

Counts how many unique proteins contain each Pfam domain, returning:

- `{Pfam_id: protein_count}`

Implementation detail:
- uses `defaultdict(set)` to avoid double-counting proteins when a domain occurs multiple times within the same protein.
- used to identify the rarest Pfam domain for candidate anchoring.

Note: the current implementation uses a fixed database/collection reference (`client["CRC_YangY_2021"]["protein_pfam_domain"]`), which should be aligned to the `DB_name` argument for general use.

---

### `matches_fg_query(FG_query_pattern, FG_candidate)`

Thin wrapper performing the regex match:

- returns `True` if `FG_query_pattern.search(FG_candidate)` is not `None`

---

## Impact on the overall pipeline

These API extensions enable end-to-end support for the project’s “improved domain search strategy” requirement:

- Users can express complex BGC/operon signatures as FGRegex-like patterns.
- The system can resolve those patterns directly against the cohort catalog (protein→gc_id mapping).
- The updated `get_FG2gc_id(...)` provides a single entry point for both exact-FG and regex-based workflows, ensuring compatibility with existing cohort-level search and visualization logic.
